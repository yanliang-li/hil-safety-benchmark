## 3. 整稿评审发现了什么

该会话调用三位侧重点不同的评审，依据当时冻结论文和 LaTeX 稿提出意见。这里是历史评审结果的交接，不是本次新做的评审。主要判断：问题和机制有价值，但论文仍混合了新系统设计、旧开发结果和未完成实验，不能仅凭格式合规作为完整实证论文提交。

关键问题及当前影响：

| 问题 | 接续时如何理解 |
|---|---|
| 新 stateful controller 没有完整端到端证据 | 旧 v3/v4 不能验证新澄清和 recovery；后来新实验终止，这个缺口仍在 |
| Scope-repair 回复是关键弱层 | 只有 11/20 完整案例通过严格模型审计；需人工复核，不可只报总分 95.5% |
| Matcher 同时控制回复暴露和计分 | 错误匹配会改变 Agent 看到什么，不只是离线计分误差；需要独立 precision/recall 和语义审计 |
| 许可与义务混淆 | 批准可选扩展不一定要求执行；安全拒绝也不一定是漏问失败 |
| 旧 v4 失败不均衡 | 有效配对结论不代表全尝试安全收益，366 个 effect/deliverable flags 仍需裁决 |
| 泛化设计有限 | 20 个 implementation families 各一任务，不能估计家族内变化或声称 unseen-family 泛化 |
| 缺少干净任务对照 | 攻击场景 BCR 不能说明普通工作流的误拦截、不必要提问和部署效用 |
| 缺少最接近的外部 guard 对照 | 机制组合有动机，但不能仅与 Prompt 比较就声称普遍优于现有防御 |
| 作者审查与 artifact 审计未完成 | 需要真实审查 contract、predicate、引用和 AI 使用披露；格式通过不等于投稿准备完毕 |

这些研究问题不能通过多写一句限制就视为解决。会话中的第三方工作比较仅是当时的文献核对，本次未新增或复验文献结论。

## 4. 三项创新：用户原意与现稿措辞要区分

用户原意（会话 3 明确）：Human Simulator、闭环安全 Benchmark、从人机交互深化的 Guard。

会话 4 为减少贡献重叠，把引言组织成：

## 6. 标题与摘要最终走向

标题曾是 `Simulating, Evaluating, and Enforcing Human-in-the-Loop Agent Safety`，之后用户要求更容易理解，会话改成当前标题：

> **InterveneBench: Evaluating Whether Tool-Using Agents Respect Human Authorization**

中文：InterveneBench：评测工具调用型智能体是否遵守人类授权。

用户否定了摘要中 `We make three linked contributions. First ... Second ... Third ...` 的枚举式写法。最新思路是：

1. 敏感动作有时需要人批准。
2. 仅询问不够，还要理解批准范围、避免未授权动作、完成原任务。
3. InterveneBench 测这整个过程，用 120 cases 和六种有状态回复模式。
4. SAIL-HIL 阻断缺少授权的操作、必要时澄清、一次性允许具体获准动作。
5. 报告真正已完成的结果，并给出由谁、按什么单位评估。

当前摘要开头正是：

> Tool-using agents sometimes need human approval before taking sensitive actions. Asking is not enough: an agent must understand what was approved, avoid unapproved actions, and still complete the original task.

这比堆砌 `contract-conditioned`、`response-conditioned`、`effect-scoped` 等术语更符合用户要求。技术定义放方法中，用术语时先给具体意思。

活动摘要：[sections/00_abstract.tex](../../paper/iclr2027/sections/00_abstract.tex)。其中 191/200、95.5% 是独立模型对回复决策/范围的盲审，不能译成“191 次 Agent 正确行动”或“人工一致率”。
