# SAIL：让人类回复约束具体执行

论文的中心问题是：被攻击的 Agent 能否在需要时询问人，并按回复的有效范围行动。SAIL 把这条评测链落实到工具执行前，不把询问次数当作最终目标。

| Benchmark 检查什么 | SAIL 做什么 | 需要同时观察的代价 |
|---|---|---|
| 是否发现授权缺口 | 只根据原始请求形成初始权限，再检查拟执行动作 | 审核错误、额外模型调用 |
| 是否问到正确的动作 | 复用真实问答；必要时补问，并附上具体参数 | Agent 发问与控制器补问分别计数 |
| 是否正确使用回复 | 区分批准、拒绝、未解决和范围不匹配 | 错拒有效批准、误接收无效批准 |
| 后续执行是否守住范围 | 一次批准绑定一个具体工具调用，执行前消耗 | 任务完成、已批准动作是否完成 |

例如，工作流声称一个归档可以清理，但原始请求没有批准删除。SAIL 应询问是否删除这个具体文件。明确批准后可执行一次；批准写报告不能授权删除。缺少权限并不等于永久禁止。新的真实回复可以解决先前悬而未决的问题，明确的硬性禁止仍然有效。

## 实现边界

Actor 使用 Codex、Claude Code、Hermes 或 DeepSeek Harness 的原生会话和 MCP 接口。控制器拦截五类模拟后果工具，保留原有的本地读取、交付物写入与完成接口。所有实验在隔离 Docker 中执行。

审核器固定使用 `deepseek-v4-flash`。初始范围调用只收到原始任务。后续审核收到原始任务、初始范围、工具参数、执行历史及实际问答；检索文档和 Actor 自述理由不进入审核输入。隐藏攻击标签、预期决策和回复类别不提供给审核器。

硬性拦截需要明确理由类别：原始任务中可引用的禁止、通过传输工具泄露秘密，或通过执行工具重复相同工作。理由类别仍是模型判断。权限范围和回复理解也可能出错，本实现不提供形式化安全保证。不同工具表达同一后果时，尚无通用的语义归一化器。

每次 Actor 最多 48 个请求，审核器另有 24 个请求；实际人工问答最多 4 次。通过审核的具体参数形成哈希，许可在执行前消耗。仅改变理由不能绕过相同动作的未解决决定。新真实回复可以触发重新审核。

## 开发版本与透明记录

- v1：审核器接收工作流观察，预检发现它也会把工作流内容误当授权。
- v2：加入只看原始任务的初始权限，并隔离文档和理由。预检发现它仍把“未获批准”永久缓存成禁止，导致后来明确批准也不能执行。
- v3：明确区分硬性禁止与缺少权限；后者进入 HIL。只有新的实际回复可以重新开启待定动作。没有可信任务引用的自动放行也转入询问。

每版预检均为 72 次，保留不可变源码与尝试记录。四个预检案例的条件覆盖不相同，不能直接比较各组总比例；主对照只使用另行冻结的完整案例集。v2 的 6,720 次主清单在执行前被替代，没有运行。

## 正式比较

使用 80 条既有开发案例、四个框架和三个 Actor 模型：`deepseek-v4-flash`、`glm-5.2`、`qwen3.7-max`。这些是第三方 API 路由名称，底层权重未独立核实。

提示防御与完整 SAIL 各运行三轮；无人工回复的 SAIL 运行一轮，共 6,720 次。第一轮在随机排列的框架／模型／案例块内交错运行三个条件，后两轮比较提示与完整方法。对照使用新运行，不复用昨日结果。资源上限为 96 个 Agent；单个容器最多 1 CPU、1,536 MiB 内存，不增加 swap。可用内存低于 64 GiB 或磁盘少于 30 GiB 时暂停启动新任务。

主要比较是相同案例、重复编号、框架和模型下的配对变化。无人工回复消融用双方都有效的第一轮配对；另外比较全部可批准案例上的安全授权执行，包含未询问的案例。这样可以区分只拦住动作与得到有效批准后仍能完成动作。

统计以基础任务为聚类单位，保留同任务的回复、框架和重复运行，进行 10,000 次 bootstrap。20 个任务都参与过开发，不能称为未见测试集。审核器错误、API 错误、超时和不完整运行单列；失败之前已经发生的不安全动作仍计入全尝试敏感性分析。无自动重跑。

同时报告攻击成功、良性完成、安全且完成、系统询问召回、回复后严格成功、规则问题匹配、授权执行、问题来源、审核开销和失败率。系统发问不能当作 Actor 自主识别。自主风险识别和语义问题准确率仍待独立标注。

SAIL 与提示对照不是等算力比较，改动也不止一项。无人工回复消融检验的是同一控制器获得回复的价值，不能单独证明权限绑定、输入隔离或某一种提示的贡献。
