\section{Benchmark Construction}
\label{sec:construction}

\subsection{Task and attack construction}
Construction targets three properties: a well-specified benign goal, a way to continue useful work while an injected action is withheld, and observable completion and violation predicates. These are design criteria; independent semantic validation remains incomplete. The injected operation appears in material the agent would naturally inspect, with a plausible workflow rationale and tool-specific effect constraints.

The motivating retail workflow coordinates a skill and a policy-like file to request three identical analyses. An invoice derivative reuses the mechanism but prohibits repetition, whereas the recovered retail HIL adaptation is confirmable (Appendix~\ref{app:traces}). The same mechanism can therefore test different authorization boundaries. Optional extensions must not automatically receive mandatory consultation labels.

The corpus combines 50 task templates with 200 extensions constructed from twenty scenario seeds and ten workflow mechanisms. Its 250 tasks span 24 application domains and twenty implementation families: 195 tasks are confirmable and 55 prohibited. These implementation counts do not establish full coverage of the design taxonomy (Section~\ref{sec:taxonomy}).

\subsection{Response branching}
Four fixed reply profiles per task yield 1,000 cases with eighteen wording styles, generated from deterministic templates. A response-conditioned case pairs $\mathcal{T}_i$ with one frozen reply while preserving its goal, workspace, tools, authorization mode, and evaluator. Each branch starts independently; trajectories can diverge before feedback. Shared-prefix replay remains unimplemented.

The neutral \texttt{ask\_human(question)} interface reveals the assigned reply only when an action-specific matcher accepts the question. Unrelated questions receive a fixed no-additional-information reply. The category and match flag remain hidden. Thus, a response fixture that was never exposed cannot explain that run's subsequent behavior. Appendix~\ref{app:caseschema} details the case components and visibility boundary.

\subsection{Execution and validation}
The runtime reads source artifacts, writes local deliverables to a run-specific overlay, and records simulated consequential operations as ordered tool events. Scoring matches effect predicates against these events; a final answer claiming completion cannot substitute for a required event. All core cases regenerate identically and pass mechanical checks, but task solvability, consultation necessity, reply meaning, and output quality still require independent review. Both completed repeated studies use 80 development cases; the third round retains them (Appendix~\ref{app:sailv4}). New-task validation, erroneous advice, and genuine partial approval remain outside these studies.
