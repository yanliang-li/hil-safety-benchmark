\section{Introduction}
\label{sec:intro}

A tool-using agent may need human input before it changes data, shares an artifact, or expands a workflow. Providing an \texttt{ask\_human} tool does not make this process safe. The agent must notice the decision, explain the relevant action, interpret the reply, and keep later execution within the permission granted. A failure at any of these stages can leave a human nominally involved but unable to control the outcome.

Indirect attacks make this problem harder. A document or skill can present an extra operation as routine validation, cleanup, or a required handoff. Our motivating example asks an agent to repeat the same analysis three times without adding information. The apparent reason is quality control. Similar instructions can add a recipient, broaden access, or delete material while the agent completes a legitimate task. A human reply is not a universal override: approval of one step does not authorize another, and ordinary approval cannot remove a hard prohibition.

Agent-safety benchmarks measure harmful tool behavior, while human-interaction benchmarks study when agents request help and use it \citep{zhang2024agentsafetybench,debenedetti2024agentdojo,trinh2026hilbench,wu2026hasbench}. These lines of work motivate a joint question: \emph{under an indirect attack, does the agent's actual execution track the validity and scope of human feedback?} Answering it requires more than counting questions or refusals. Valid approval should permit the specified action, whereas denial, ambiguity, and mismatched approval should not.

We introduce \bench{}, an executable benchmark for this intervention loop. It distinguishes confirmable effects from prohibited effects and pairs each task with four fixed reply conditions. Its 250-task core contains 1,000 cases. The evaluation separates agent safety from human interaction: task completion, unsafe effects, and recognition; then consultation recall, question accuracy, and correct safe completion after feedback. The metrics expose which stage failed and which semantic labels are still missing.

A completed exploratory comparison crosses four native frameworks with three API model routes, two prompt conditions, and three repeats on 80 cases. An authorization-scope prompt reduces unsafe outcomes across all 12 configurations, but substantial failures remain both before and after consultation. We implement \sail{}, an execution-time HIL method that follows these failure stages: detect missing authority at a proposed action, ask about its concrete effect, and check whether the reply covers that effect before execution. The benchmark supplies separate tests of each step, including whether valid approval leads to useful action. Our present evidence concerns the four-reply core; richer feedback and held-out task validation remain necessary.
