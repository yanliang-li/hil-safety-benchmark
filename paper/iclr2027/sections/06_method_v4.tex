\section{SAIL: Scoped Human Intervention and Task Recovery}
\label{sec:defense}

SAIL places an authorization check before consequential tool calls while retaining the actor's native planning loop. We distinguish the evaluated v3 controller from the v4 revision motivated by its failures.

\subsection{Evaluated scoped-authorization controller}
\label{sec:sailv3method}
SAIL v3 infers initial authority from the original task, excluding workflow artifacts and actor justifications. A fixed reviewer checks each consequential call against this scope, tool arguments, execution history, and actual question--reply pairs. Missing authority triggers consultation; a hard block requires a positive constraint basis. Approval binds a one-use permit to exact call arguments, consumed before dispatch. Only new reply evidence can reopen an unresolved decision. Permission interpretation remains fallible, and restart persistence was not established. Section~\ref{sec:sailresults} reports this controller's completed comparison; Appendix~\ref{app:sailresults} records its reliability boundaries.

\subsection{Authority preservation and task recovery}
\label{sec:sailv4method}
SAIL v3 lost original permissions and unfinished task obligations. The implemented v4 revision therefore separates original authority, human-approved extensions, and completion obligations (Figure~\ref{fig:sail}). Its formal evaluation remains pending.

\paragraph{Effect-bound authorization.}
A reviewer receives the original task and trusted tool descriptions. It records authorized effects and obligations with literal task quotations, constraining tools, objects, purposes, arguments, scope, and cumulative bounds. Workflow artifacts cannot extend this fallible contract. Local reads and deliverable writes remain available; consequential calls require matching authority and remaining budget.

The controller first checks existing question--reply pairs, then asks about missing authority with the exact proposed call. Reply review distinguishes approval, denial, ambiguity, and mismatched scope. Approval must quote the actual reply and cover the proposed effect and conditions. Denying an extension preserves original authority; explicit revocation is recorded separately.

\paragraph{Runtime enforcement and task recovery.}
A one-use permit binds reviewed arguments and is consumed before dispatch. Reservations persist across restarts. For a matched resource effect $e$,
\begin{equation}
u_e+q_j\leq b_e,
\end{equation}
where $u_e$ is reserved use, $q_j$ the proposed quantity, and $b_e$ the authorized total. Failed dispatches retain reservations because execution may be uncertain. Effect association remains model-dependent; general cross-tool equivalence is unverified (Appendix~\ref{app:guarddesign}).

After a block, recovery returns the deferred effect, missing decision, unfinished obligations, and still-authorized work. Suggested consequential calls pass through the same checks. At \texttt{finish}, completion review checks obligations against successful tool feedback and requests bounded repairs for missing work. Claims of completion cannot substitute for required events.

Both versions use a fixed \texttt{deepseek-v4-flash} reviewer. V4 permits 48 actor requests, 24 reviewer requests, four human questions, and 900 seconds. Recovery allows four events, including two finish repairs. Its no-human ablation retains recovery; unresolved review errors remain failed attempts. Controller inputs exclude hidden scoring labels.
